# CLAUDE.md

Firmware for **Eveningstar**, an open-source interface board for Morningstar solar charge controllers. It talks to the charge controller over its MeterBus port and exposes it over Ethernet/WiFi. This repo holds only the firmware; the board design lives at https://github.com/ciaassured/eveningstar-hardware.

The project was originally generated by `esp-generate` for Espressif MCUs.

## Hardware

- MCU: ESP32-C6 with WiFi. Board also has Ethernet, on-board flash, and a ~32 kHz crystal for the RTC.
- USB-C is wired directly to the ESP32-C6's built-in USB Serial/JTAG controller. This is the primary way to flash and debug the board. A separate debug header exists but is secondary.
  - Do not reconfigure the USB pins (GPIO12/GPIO13 on the C6); doing so drops the USB Serial/JTAG link and breaks flashing/debugging over USB-C.
- There is **no reset button**. Resets during development come from the host over USB Serial/JTAG (e.g. probe-rs). Do not assume a user can physically reset or enter download mode.
- One user button. It is a user-facing control (e.g. factory reset, start a WiFi configuration hotspot), not a reset/boot button. Firmware owns its behaviour.
- One white status LED, used to show the device's current state to the user.
- MeterBus interface: isolated, 9600 baud UART-like link. The board hardware does the level shifting/isolation, so the firmware only drives a plain UART.
  - When the bus is connected, the interface echoes every transmitted byte back on RX. Use the echo to verify transmission is working (no/incorrect echo means bus disconnected or faulty), and consume the echoed bytes before parsing the controller's response.
- Pin assignments and board-revision details live in the `eveningstar-board` BSP crate (`crates/eveningstar-board`); keep board knowledge there, not in the application crate.

## Development environment (Nix)

- The tooling comes from the Nix flake's dev shell (`nix/devshell.nix`), not from the system. A tool missing from the plain shell (e.g. `probe-rs: command not found`) does not mean it is unavailable: run it through the dev shell.
  - Non-interactive: `nix develop --command <cmd>`, e.g. `nix develop --command probe-rs list` or `nix develop --command cargo run --release`.
  - The dev shell provides `probe-rs`, `espflash`, `esptool`, `esp-generate`, `gdb`, `lefthook`, ESP-IDF (`idf.py`, `IDF_TARGET=esp32c6`), and the flake's own commands: `eveningstar-checks`, `flash-boot`, `flash-app`, `flash-all`, `esp-wipe`, `bootloader-menuconfig`.
  - The Rust toolchain comes from `rust-toolchain.toml` (rustup), so `cargo` works with or without the dev shell.
- Checks: `nix run .#checks` runs everything; `nix run .#checks -- lint` (rustfmt + clippy with `-D warnings`), `nix run .#checks -- build` (release build) and `nix run .#checks -- test` (tests of the crates that also build on the host, run on the host target) run one group. The crates that also build on the host are listed in `host_crates` in `nix/checks.nix`; clippy checks them for both targets, and keeps their features out of the firmware's lint. They build into `target/checks`. The lefthook Git hooks run `lint` on pre-commit and `build` and `test` on pre-push, and CI uses the same entry point.
- Flashing: `cargo run` flashes and streams defmt logs through probe-rs and keeps running until stopped. `flash-boot`, `flash-app` and `flash-all` write the bootloader, partition table and OTA app layout defined in `nix/board.nix` with esptool.
- Board layout (chip, flash size/mode, partitions) is defined once in `nix/board.nix`.

## Project-specific notes

- Target chip: `esp32c6`; keep dependencies, HAL features, and examples compatible with this chip.
- Check the `generator parameters:` comments in `crates/eveningstar/src/main.rs` before changing code that depends on selected generation options.
- Cargo workspace: crates live flat under `crates/`. Versions, edition, rust-version, shared dependencies, lints and profiles are defined once in the root `Cargo.toml`; member crates inherit them with `.workspace = true` and `[lints] workspace = true`.
- This is a `#![no_std]` / `#![no_main]` project. Avoid `std`; use `core` and embedded-friendly crates.
- `alloc` is not enabled. Avoid heap-backed types such as `Vec`, `String`, `Box`, and boxed futures unless you add and initialize an allocator.
- `.cargo/config.toml` contains the generated target, runner, build flags, and `[env]` defaults. Espressif crates expose additional configuration through environment variables; use `esp-config` to inspect/set those options. The linked "Additional configuration" sections for the enabled Espressif crates document crate-specific variables; keep project-specific defaults in `[env]` instead of hard-coding them in source.
- Logging uses `defmt`; the default filter is `DEFMT_LOG=info` in `.cargo/config.toml` and can be overridden from the environment.
- `cargo run` uses `probe-rs` as configured in `.cargo/config.toml` for flashing, RTT/defmt and debugging. On this board probe-rs connects through the ESP32-C6's built-in USB Serial/JTAG over the USB-C port; no external probe is needed.
- If flashing or debugging fails, check `probe-rs list`, probe permissions/udev rules, board wiring/JTAG support, and that the `--chip` in `.cargo/config.toml` matches the target.
